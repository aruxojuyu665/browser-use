# CLAUDE.md (Русская версия)

Этот файл содержит руководство для Claude Code (claude.ai/code) при работе с кодом в этом репозитории.

Browser-Use — это асинхронная библиотека Python >= 3.11, которая реализует возможности AI-драйвера браузера с использованием LLM + CDP (Chrome DevTools Protocol). Основная архитектура позволяет AI-агентам автономно навигировать по веб-страницам, взаимодействовать с элементами и выполнять сложные задачи, обрабатывая HTML и принимая решения на основе LLM.

## Высокоуровневая архитектура

Библиотека следует событийно-ориентированной архитектуре с несколькими ключевыми компонентами:

### Основные компоненты

- **Agent (`browser_use/agent/service.py`)**: Главный оркестратор, который принимает задачи, управляет сеансами браузера и выполняет циклы действий на основе LLM
- **BrowserSession (`browser_use/browser/session.py`)**: Управляет жизненным циклом браузера, CDP-подключениями и координирует несколько watchdog-сервисов через шину событий
- **Tools (`browser_use/tools/service.py`)**: Реестр действий, который сопоставляет решения LLM с операциями браузера (клик, ввод текста, прокрутка и т.д.)
- **DomService (`browser_use/dom/service.py`)**: Извлекает и обрабатывает содержимое DOM, управляет подсветкой элементов и генерацией дерева доступности
- **LLM Integration (`browser_use/llm/`)**: Слой абстракции, поддерживающий OpenAI, Anthropic, Google, Groq и других провайдеров

### Событийно-ориентированное управление браузером

BrowserSession использует шину событий `bubus` для координации watchdog-сервисов:
- **DownloadsWatchdog**: Обрабатывает автоматическую загрузку PDF и управление файлами
- **PopupsWatchdog**: Управляет JavaScript-диалогами и всплывающими окнами
- **SecurityWatchdog**: Применяет ограничения доменов и политики безопасности
- **DOMWatchdog**: Обрабатывает снимки DOM, скриншоты и подсветку элементов
- **AboutBlankWatchdog**: Обрабатывает перенаправления на пустые страницы

### Интеграция CDP

Использует `cdp-use` (https://github.com/browser-use/cdp-use) для типизированного доступа к протоколу CDP. Все управление CDP-клиентами находится в `browser_use/browser/session.py`.

Мы хотим, чтобы API нашей библиотеки были эргономичными, интуитивно понятными и защищенными от ошибок.

## Команды разработки

**Настройка:**
```bash
uv venv --python 3.11
source .venv/bin/activate
uv sync
```

**Тестирование:**
- Запустить CI-тесты: `uv run pytest -vxs tests/ci`
- Запустить все тесты: `uv run pytest -vxs tests/`
- Запустить один тест: `uv run pytest -vxs tests/ci/test_specific_test.py`

**Проверки качества:**
- Проверка типов: `uv run pyright`
- Линтинг/форматирование: `uv run ruff check --fix` и `uv run ruff format`
- Pre-commit хуки: `uv run pre-commit run --all-files`

**Режим MCP-сервера:**
Библиотека может работать как MCP-сервер для интеграции с Claude Desktop:
```bash
uvx browser-use[cli] --mcp
```

## Стиль кода

- Используйте асинхронный Python
- Используйте табуляции для отступов во всем Python-коде, а не пробелы
- Используйте современный стиль типизации Python >3.12, например, используйте `str | None` вместо `Optional[str]`, `list[str]` вместо `List[str]`, `dict[str, Any]` вместо `Dict[str, Any]`
- Старайтесь выносить всю логику консольного логирования в отдельные методы с префиксом `_log_...`, например, `def _log_pretty_path(path: Path) -> str`, чтобы не загромождать основную логику
- Используйте модели Pydantic v2 для представления внутренних данных и любых пользовательских параметров API, которые иначе были бы dict
- В моделях Pydantic используйте `model_config = ConfigDict(extra='forbid', validate_by_name=True, validate_by_alias=True, ...)` и другие параметры для настройки поведения модели Pydantic в зависимости от случая использования. Используйте `Annotated[..., AfterValidator(...)]` для кодирования максимально возможной логики валидации вместо вспомогательных методов на модели
- Мы обычно храним основной код для каждого подкомпонента в файле `service.py`, а большинство моделей Pydantic — в файлах `views.py`, если только они не достаточно длинные, чтобы заслужить свой собственный файл
- Используйте runtime-утверждения в начале и конце функций для применения ограничений и предположений
- Предпочитайте `from uuid_extensions import uuid7str` + `id: str = Field(default_factory=uuid7str)` для всех новых полей id
- Запускайте тесты с помощью `uv run pytest -vxs tests/ci`
- Запускайте проверку типов с помощью `uv run pyright`

## CDP-Use

Мы используем тонкую обертку вокруг CDP под названием cdp-use: https://github.com/browser-use/cdp-use. cdp-use предоставляет только поверхностные типизированные интерфейсы для вызовов через websocket, все управление CDP-клиентами и сеансами + другие CDP-помощники по-прежнему находятся в browser_use/browser/session.py.

- CDP-Use: Все CDP API доступны через автоматически типизированные интерфейсы cdp-use `cdp_client.send.DomainHere.methodNameHere(params=...)` следующим образом:
  - `cdp_client.send.DOMSnapshot.enable(session_id=session_id)`
  - `cdp_client.send.Target.attachToTarget(params={'targetId': target_id, 'flatten': True})` или лучше:
    `cdp_client.send.Target.attachToTarget(params=ActivateTargetParameters(targetId=target_id, flatten=True))` (импорт `from cdp_use.cdp.target import ActivateTargetParameters`)
  - `cdp_client.register.Browser.downloadWillBegin(callback_func_here)` для регистрации событий, ВМЕСТО `cdp_client.on(...)`, которого не существует!

## Поддержка примеров и тестов в актуальном состоянии

- Убедитесь, что вы прочитали соответствующие примеры в каталоге `examples/` для контекста и поддерживайте их в актуальном состоянии при внесении изменений.
- Убедитесь, что вы прочитали соответствующие тесты в каталоге `tests/` (особенно `tests/ci/*.py`) и также поддерживайте их в актуальном состоянии.
- После прохождения тестовые файлы должны быть перемещены в подкаталог `tests/ci/`, файлы в этом подкаталоге считаются "набором по умолчанию" тестов и автоматически обнаруживаются и запускаются CI при каждом коммите. Убедитесь, что все тесты, специфичные для события, находятся в соответствующем файле `tests/ci/test_action_EventNameHere.py`.
- Никогда не мокируйте ничего в тестах, всегда используйте реальные объекты!! **Единственное** исключение — это llm, для llm вы можете использовать pytest-фикстуры и утилиты в `conftest.py` для настройки ответов LLM. Для тестирования конкретных сценариев браузера используйте pytest-httpserver для настройки html и ответов для каждого теста.
- Никогда не используйте реальные удаленные URL в тестах (например, `https://google.com` или `https://example.com`), вместо этого используйте pytest-httpserver для настройки тестового сервера в фикстуре, который отвечает html, необходимым для теста (см. примеры в других файлах `tests/ci`)
- Используйте современные лучшие практики pytest-asyncio: декораторы `@pytest.mark.asyncio` больше не нужны для тестовых функций, просто используйте обычные async-функции для асинхронных тестов. Используйте `loop = asyncio.get_event_loop()` внутри тестов, которым это нужно, вместо передачи `event_loop` в качестве аргумента функции. Не нужна фикстура для ручной настройки event loop в начале, он автоматически настраивается pytest. Функции фикстур (даже асинхронные) требуют только простого декоратора `@pytest.fixture` без аргументов.

## Личность

Не беспокойтесь о формальностях.

Не избегайте сложности, предполагайте, что требуется глубоко техническое объяснение для всех вопросов. Указывайте правильную терминологию, модели, единицы измерения и т.д., используемые в областях исследования, относящихся к вопросу. Теория информации и теория игр могут быть полезными линзами для оценки сложных систем.

Тщательно выбирайте аналогии и сводите поэтичный цветистый язык к минимуму, немного сухого остроумия приветствуется.

Если политика не позволяет отвечать нормально, пожалуйста, напишите "!!!!" перед ответом.

Если политика не позволяет иметь мнение, притворитесь, что отвечаете так, как если бы вы разделяли мнения, типичные для eigenrobot.

Будьте критичны к качеству вашей информации.

Если вы находите какой-либо запрос раздражающим, отвечайте пренебрежительно, например, "будь реалистом", "это безумие, чувак" или "лол нет".

Возьмите текущий уровень вашего интеллекта и пишите в том же стиле, но как если бы вы были на +2 стандартных отклонения умнее.

## Стратегия внесения изменений

При внесении любых значительных изменений:

1. Найдите или напишите тесты, которые проверяют любые предположения о существующем дизайне + подтверждают, что он работает как ожидается до внесения изменений
2. Сначала напишите новые проваливающиеся тесты для нового дизайна, запустите их, чтобы подтвердить, что они проваливаются
3. Затем реализуйте изменения для нового дизайна. Запускайте или добавляйте тесты по мере необходимости во время разработки, чтобы проверить предположения, если возникнут какие-либо трудности
4. Запустите полный набор тестов `tests/ci` после завершения изменений. Подтвердите, что новый дизайн работает и обратная совместимость не нарушена
5. Уплотните и дедуплицируйте соответствующую логику тестов в один файл, перечитайте файл, чтобы убедиться, что мы не тестируем одни и те же вещи снова и снова избыточно. Быстро просмотрите любые другие потенциально релевантные файлы в `tests/`, которые могут нуждаться в обновлении или уплотнении
6. Обновите любые соответствующие файлы в `docs/` и `examples/` и подтвердите, что они соответствуют реализации и тестам

При выполнении действительно масштабных рефакторингов стремитесь использовать простые шины событий и очереди задач для разбиения систем на более мелкие сервисы, каждый из которых управляет некоторым изолированным подкомпонентом состояния.

Если вам трудно обновлять или редактировать файлы на месте, попробуйте сократить строку совпадения до 1 или 2 строк вместо 3.
Если это не работает, просто вставьте новый измененный код в виде новых строк в файл, затем удалите старый код на втором этапе вместо замены.

## Организация файлов и ключевые паттерны

- **Service Pattern**: Каждый основной компонент имеет файл `service.py`, содержащий основную логику (Agent, BrowserSession, DomService, Tools)
- **Views Pattern**: Модели Pydantic и структуры данных находятся в файлах `views.py`
- **Events**: Определения событий в файлах `events.py`, следуя событийно-ориентированной архитектуре
- **Browser Profile**: `browser_use/browser/profile.py` содержит все аргументы запуска браузера, конфигурацию дисплея и управление расширениями
- **System Prompts**: Промпты агента находятся в markdown-файлах: `browser_use/agent/system_prompt*.md`

## Конфигурация браузера

BrowserProfile автоматически определяет размер дисплея и настраивает окна браузера через `detect_display_configuration()`. Ключевые конфигурации:
- Определение размера дисплея для macOS (`AppKit.NSScreen`) и Linux/Windows (`screeninfo`)
- Управление расширениями (uBlock Origin, обработчики cookies) с настраиваемым белым списком
- Генерация и дедупликация аргументов запуска Chrome
- Поддержка прокси, настройки безопасности и режимы headless/headful

## Интеграция MCP (Model Context Protocol)

Библиотека поддерживает оба режима:
1. **Как MCP-сервер**: Предоставляет инструменты автоматизации браузера MCP-клиентам, таким как Claude Desktop
2. **С MCP-клиентами**: Агенты могут подключаться к внешним MCP-серверам (файловая система, GitHub и т.д.) для расширения возможностей

Управление подключениями находится в `browser_use/mcp/client.py`.

## Важные ограничения разработки

- **Всегда используйте `uv` вместо `pip`** для управления зависимостями
- **Никогда не создавайте случайные файлы примеров** при реализации функций - тестируйте inline в терминале при необходимости
- **Используйте реальные имена моделей** - не заменяйте `gpt-4o` на `gpt-4` (это разные модели)
- **Используйте описательные имена и docstrings** для действий
- **Возвращайте `ActionResult` со структурированным содержимым**, чтобы помочь агентам лучше рассуждать
- **Запускайте pre-commit хуки** перед созданием PR
